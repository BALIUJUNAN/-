# 阶段 5：应用接管与一次性迁移

## 目标

将员工、商品、供应商、会员和系统配置从文本文件主路径切换到
AbyssDB，同时保留现有 C 业务接口的指针语义。旧文件只在首次启动时作为迁移输入，
不再作为运行时写入目标。

## 已实现

- `sm_app_context` 统一管理应用级仓储的打开、checkpoint 和关闭。
- `sm_legacy_import_if_needed` 先严格解析全部来源，再用一个写事务导入全部实体、
  配置和完成标记；任何记录失败都整批回滚。
- 显式 ID 导入保留旧业务键，并在同一事务中提升员工、商品、供应商和会员计数器水位。
- 迁移标记保存状态、来源指纹、时间和记录数，防止重复导入。
- 基础实体查询直接读仓储；原哈希表和会员链表降级为可丢弃的惰性对象缓存。
- 写路径先提交 AbyssDB，成功后再更新缓存；条码和手机号缓存会撤销旧键。
- 员工列表、商品列表、低库存查询、库存报表和会员列表不再扫描全局哈希表。
- 备份前强制 checkpoint，基础数据备份对象改为 `supermarket.abdb` 及 journal。

## 迁移不变量

1. 迁移完成标记与导入数据必须同事务提交。
2. 已有基础数据但没有迁移标记时拒绝自动合并，返回 `SM_REPO_CONFLICT`。
3. 旧文件不被删除、改名或回写，可用于人工审计和回滚。
4. 空来源也写入完成标记，防止日后意外导入新出现的旧文件。
5. 数据库是唯一真相；缓存不参与恢复，也不能覆盖未加载记录。

## 验收

`make test-phase5` 覆盖：

- 五类旧数据的原子导入与精确查询。
- 导入后计数器从历史最大 ID 继续。
- 重启后识别完成标记，不重复导入。
- 坏文件整批回滚，修复后可在同一数据库上重试。
- 显式 checkpoint 通路可用。

## 边界

销售、采购、排班、促销、多门店、财务和日志聚合仍使用旧文本表，由后续阶段按业务
事务边界逐个迁移。阶段 5 不引入长期双写。
