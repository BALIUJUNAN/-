# 阶段 6：销售聚合与原子结算

## 目标

将 Sale/SaleItem、挂单恢复、销售统计和结算事务迁移到 AbyssDB。订单状态、商品库存
和会员积分/累计消费必须一次提交，文本文件只允许作为首次迁移输入。

## 已实现

- Sale/SaleItem 使用稳定整数实体：金额为分，数量为千分单位，时间为 `int64_t`。
- TLV codec 拒绝缺字段、越界字符串、非法状态和损坏值。
- 主键及状态、完成时间、收银员时间、会员时间、订单明细前缀索引已接入仓储。
- 销售与明细 ID 使用持久化 counter；显式迁移会推进 counter 水位。
- 独立阶段 6 迁移标记，不依赖基础实体迁移标记，可重复执行且失败整批回滚。
- 挂单创建、明细添加、挂起更新、取消和启动恢复均以数据库为准；链表仅为可丢弃缓存。
- 结算先展开并合并套装库存，再在一个 UOW 中完成订单、库存和会员更新。
- 套装交易日志和小票是提交后的投影，不参与数据库提交结果。
- 销售报表、CSV/HTML 导出、盈亏收入、日结、今日仪表盘和热销榜均读取数据库。

## 事务不变量

1. 只有 Pending 订单可以添加明细、取消或完成。
2. 库存不足时订单、所有商品和会员必须保持原值。
3. 完成订单的收银员和创建时间继承持久化挂单，调用方不能篡改。
4. Sale/SaleItem 在订单完成后保留，用于审计、报表和重启恢复。
5. 数据库提交成功后才刷新缓存并生成日志/小票；投影失败不能回滚已完成交易。
6. 已迁移的 `sales.txt`、`pending_sales.txt`、`sale_item.txt` 不再被运行时读取或写入。

## 验收

`make test-phase6` 覆盖：

- 创建挂单与明细并按前缀查询。
- 库存不足时跨实体事务完整回滚。
- 成功结算同时更新订单、库存和会员，checkpoint/reopen 后保持一致。
- 取消挂单同时删除其全部明细。
- 旧销售数据精确保留 ID，并从历史最大 ID 继续分配。
- 重复迁移跳过；坏行不写数据或标记，修复后可以重试。

## 阶段边界

StockLog 已在阶段 7 迁移为数据库实体，并纳入销售结算事务；AuditLog 仍是提交后的
文本投影，将在审计阶段迁移为数据库实体。
储值卡扣款已在阶段 10 纳入销售 UOW，不再使用失败补偿；审计日志将在最终审计阶段
纳入同一业务事务。
