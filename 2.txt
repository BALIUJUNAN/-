================================================================================
  超市管理系统 - 学习指南 第二部分
  负责人：你
  负责模块：买卖交易（sale.c + purchase.c）
================================================================================

【开篇：你的角色是什么？】

你现在是超市的"进销存"负责人。进 = 采购（purchase.c），销 = 销售（sale.c），存 = 库存变动记录。

简单说：货怎么进来、怎么卖出去、库存怎么变的，全归你管。


================================================================================
第一关：销售流程（sale.c）—— 从扫码到打印小票
================================================================================

【生活类比：收银台的一天】

想象你是收银员，一天的工作流程：

早上开门 → 有人来买东西 → 扫码 → 算钱 → 收钱 → 打印小票 → 下一位

对应的代码流程：

1. 创建订单 create_sale()
   顾客把商品放到收银台，你先开一张新单子。
   代码里：生成一个订单号，状态设为"挂单"（SALE_PENDING），就像把单子夹在夹子上等着。

2. 添加商品 add_sale_item() / scan_and_sell()
   扫码枪扫一下商品条码，系统自动找到商品信息，加入订单。
   代码里：先查条码哈希表找到商品，检查库存够不够，算出小计金额，加入明细链表。
   特殊情况：如果扫到的是套装条码（比如"零食大礼包"），要走套装专用流程。

3. 完成收银 complete_sale() —— 这是最核心的函数！
   顾客说"结账"，你做以下事情：
   a) 算总价：把所有商品的小计加起来
   b) 算折扣：如果有额外手动折扣（比如抹零），算出折扣金额
   c) 扣库存：每件商品的库存数量减掉卖出的数量
   d) 记日志：每扣一次库存，写一条库存变动记录（出库）
   e) 写销售记录：把这笔交易保存到 sales.txt
   f) 从挂单列表移除：单子已经完成了，从"等待处理"的列表里拿掉
   g) 打印小票：把商品明细、金额、找零等信息传给打印机

   这整个过程要"原子化"——要么全成功，要么全失败。不能出现"钱收了但库存没扣"的情况。

4. 挂单 hang_sale()
   顾客说"我先去拿个东西，等下来结账"。
   你把当前订单保存到 pending_sales.txt，回头顾客来了继续处理。

5. 取消订单 cancel_sale()
   顾客说"不要了"。你把订单从内存中删掉。


【关键数据结构】

全局变量 g_pending_sales 是一个链表，存着所有还没结账的订单。
就像收银台上夹着的一排单子，等待处理。

全局变量 g_sale_items 存着所有订单的商品明细。
一个订单可以有多条明细（买了3种商品就有3条）。

全局变量 g_stock_logs 存着所有库存变动记录。
每次入库/出库/盘点都会记一条，就像仓库的进出账本。


【sale.c 的文件读写】

- sales.txt：已完成的销售记录，追加写入（一行一笔交易）
  格式：订单号|收银员ID|会员ID|总金额|折扣|实付|支付方式|状态|创建时间|完成时间

- pending_sales.txt：挂单记录
  格式同上，但状态是"挂单"

- stock_log.txt：库存变动日志
  格式：ID|商品ID|类型(入库/出库)|变动数量|变动前库存|变动后库存|操作人|备注|时间


================================================================================
第二关：库存管理 —— 货架上的数怎么变
================================================================================

【生活类比】

库存就像你钱包里的钱：
- 进货 = 往钱包里放钱（库存增加）
- 卖货 = 从钱包里拿钱（库存减少）
- 盘点 = 数数钱包里还有多少钱（核对实际库存和系统记录）

【record_stock_log() —— 记账本】

每次库存变动都要记一笔，参数包括：
- 商品ID：哪个商品
- 类型：入库/出库/盘点/调整
- 变动前库存：变动之前有多少
- 变动后库存：变动之后有多少
- 操作人：谁做的这个操作
- 备注：为什么变动（比如"销售出库"、"采购入库"）

就像银行流水账——每一笔进出都有记录，出问题了可以追溯。

【check_stock_alert() —— 缺货预警】

遍历所有商品，找出库存低于最低预警线的。
就像冰箱里的牛奶快喝完了，系统提醒你"该进货了"。

【inventory_check() —— 盘点】

把系统记录的库存和你实际数出来的数量对比。
如果对不上，说明有损耗或录入错误。


================================================================================
第三关：采购流程（purchase.c）—— 货怎么进来
================================================================================

【生活类比：采购的审批流程】

你在公司要买一台电脑：
1. 你填采购申请单（create_purchase）
2. 部门经理审批（approve_purchase 或 reject_purchase）
3. 审批通过后，IT部门收货（receive_purchase）
4. 货入库，库存增加

对应的代码流程：

1. create_purchase(采购信息)
   创建采购订单，状态设为"待审核"（PURCHASE_PENDING）。
   同时记录一条事务日志："XXX创建了采购订单#123"。

2. add_purchase_item(订单ID, 明细)
   添加要采购的商品：什么商品、买多少、单价多少。
   可以一次采购多种商品。

3. approve_purchase(订单ID, 审批人ID)
   店长审批通过，状态变为"已审核"（PURCHASE_APPROVED）。
   记录事务日志。

4. reject_purchase(订单ID, 审批人ID)
   店长拒绝，状态变为"已拒绝"。
   比如：进货价太贵了，不批。

5. receive_purchase(订单ID, 操作人ID)
   库管收到货了！这是核心操作：
   - 遍历采购明细
   - 每个商品的库存 += 采购数量
   - 记录库存变动日志（入库）
   - 更新已收货数量
   - 订单状态变为"已完成"（PURCHASE_COMPLETED）

6. calculate_purchase_total(订单ID)
   计算采购总额 = 各商品的(数量 × 单价)之和。

7. list_purchases(状态, 数量)
   按状态列出采购订单：所有待审核的、所有已完成的等。


【purchase.c 的文件读写】

- purchase.txt：采购订单
  格式：订单ID|供应商ID|供应商名|创建人|审批人|状态|总金额|创建时间|审批时间|完成时间

- purchase_item.txt：采购明细
  格式：明细ID|订单ID|商品ID|商品名|数量|单价|已收货数量

- transaction.log：事务日志（审计追踪）
  格式：ID|类型|关联ID|操作|详情|操作人|时间

事务日志记录所有关键操作，就像银行的审计日志——谁在什么时间做了什么，全部有据可查。


================================================================================
第四关：sale.c 和 purchase.c 的协作关系
================================================================================

【生活类比】

销售和采购就像跷跷板的两端：
- 卖出去了 → 库存减少 → 触发采购需求
- 买进来了 → 库存增加 → 可以继续卖

具体协作：

1. sale.c 卖出商品 → 调用 supermarket.c 的 find_product_by_id() 查商品 → 修改库存 → 更新商品信息

2. purchase.c 采购入库 → 同样调用 find_product_by_id() → 增加库存 → 更新商品信息

3. 两边都依赖 supermarket.c 提供的商品查询和库存更新功能

4. sale.c 还依赖 marketing.c 的促销计算和会员积分功能


================================================================================
第五关：深入理解 complete_sale() 函数
================================================================================

这个函数是整个销售模块的"心脏"，让我们把它拆开来看：

【第1步：找到订单】
Sale *sale = find_pending_sale(sale_id);
在挂单链表里找到这笔订单，找不到就返回-1。

【第2步：算钱】
float total = calculate_sale_total(sale_id);
遍历所有明细，把小计加起来。

float extra_discount = total * (discount / 100.0f);
如果收银员输入了额外折扣百分比，算出折扣金额。

sale->final_amount = total - extra_discount;
最终金额 = 总额 - 折扣。

【第3步：扣库存】
for (每个商品明细) {
    if (是套装) {
        调用 deduct_combo_stock() 扣减套装内各商品的库存
    } else {
        商品库存 -= 卖出数量
        record_stock_log() 记录出库日志
    }
}

【第4步：保存销售记录】
save_sale_record(sale);  // 写入 sales.txt

【第5步：清理挂单】
从 g_pending_sales 链表中删除这笔订单。

【第6步：打印小票】
构建 Receipt 结构体，填入店铺信息、商品明细、金额、积分等，
调用 printer_print_receipt() 输出到热敏打印机。


================================================================================
第六关：常见问题与理解难点
================================================================================

Q1: 为什么销售订单要有"挂单"状态？
A: 顾客可能中途离开（比如去拿忘了的东西），你不能直接取消订单，也不能完成订单。
   挂单就是"暂停保存"，等顾客回来继续。

Q2: 库存扣减为什么要在保存销售记录之前？
A: 这是事务一致性的考虑。如果先保存销售记录，再扣库存时失败了，
   就会出现"卖了但没扣库存"的数据不一致问题。所以先扣库存，再保存记录。

Q3: 采购为什么要分"待审核→已审核→已完成"三个状态？
A: 模拟真实的审批流程。不是谁想买就能买的，需要店长批准。
   这也是权限管理的体现。

Q4: 事务日志（transaction.log）有什么用？
A: 审计追踪。出了问题可以查：谁在什么时间做了什么操作。
   就像银行的监控录像——平时没用，出事了是关键证据。

Q5: stock_log.txt 和 transaction.log 有什么区别？
A: stock_log.txt 只记录库存变动（入库/出库/盘点）。
   transaction.log 记录所有关键业务操作（创建订单、审批、收货等）。
   前者关注"货"，后者关注"事"。


================================================================================
总结：第二部分的核心要点
================================================================================

1. 销售流程：创建订单 → 添加商品 → 完成收银（扣库存+记日志+打印小票）
2. 采购流程：创建订单 → 审批 → 收货入库（加库存+记日志）
3. complete_sale() 是最核心的函数，承担了算钱、扣库存、记日志、打印等多项职责
4. 库存是连接销售和采购的桥梁：卖出减少，买入增加
5. 事务日志记录所有关键操作，用于审计追踪
6. 所有数据以"|"分隔的文本格式存储，追加写入日志文件，全量覆盖写入状态文件

记住一句话：sale.c 管"卖"，purchase.c 管"买"，两者的交汇点是"库存"——一个减，一个加。
